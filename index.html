The crime scene

案发现场：订单接口突然慢了

先别急着执行 CREATE INDEX。我们需要确认：慢在哪里、数据库读了多少、估算错了多少，以及这个接口究竟在向数据库索取什么。

案件 #2026-ORDER-LIST

  • 接口GET /api/orders
  • 过滤租户、状态、近 30 天、可选用户
  • 排序创建时间倒序
  • 分页LIMIT 50 OFFSET 200000
  • 数据量8.6 亿行，持续写入
  • 现象CPU 不高，存储读突增，接口偶发超时

以上数字是教学案例，不是通用基准；真正结论必须来自你的执行计划和 I/O 数据。

数据库优化的第一问不是“有没有索引”，而是：为了得到 50 行，它做了多少无用功？

Question 01

读了多少？

看实际行数、循环次数、共享缓冲命中与读入缓冲页的数量。返回 50 行不代表只处理了 50 行。

Question 02

估得准吗？

优化器根据统计信息选计划。估算 100 行、实际 100 万行，后续每一步都可能选错。

Question 03

顺序匹配吗？

过滤、排序、返回列与索引布局是否一致，决定了扫描范围、排序开销与是否回表。

破案主线：访问路径 = 数据如何存放 × 查询如何描述 × 优化器如何估算 × 当时的缓存与并发。
01

Pages before rows

数据库真正搬运的是“页”

SQL 写的是行，存储引擎付出的主要 I/O 单位却是页。理解这一点，才知道为什么“只查一行”也可能很贵。

没有索引：逐页找证据

顺序扫描会读取表的数据页，逐行判断谓词。它并不“低级”：当查询要返回表中很大比例的数据时，连续批量读取通常比大量随机跳转更划算。

所以优化器选择 Seq Scan 不等于数据库犯错。也许是选择性太差、表很小、统计信息失真，或随机 I/O 成本更高。

有索引：先找地址，再拿证据

PostgreSQL 的普通索引项通常指向堆表中的 tuple（可理解为页号 + 页内位置）；索引把候选范围缩小，再去堆页验证可见性并取完整行。

这次“从索引跳到表”的动作，就是常说的回表。候选越多、物理位置越分散，随机访问代价越明显。

相对工作量把当前最优路径记为 1.0×；它不是耗时或 PostgreSQL 的真实 cost。模型假设命中行在堆页中随机分布，真实结果还受物理相关性、可见性、返回列、并发与配置影响。

选择性描述的是某个谓词能把数据缩小到什么程度。status = 'PAID' 可能命中 70%，单独索引价值有限；但在 tenant_id = 42 AND status = 'PAID' AND created_at >= ... 里，它是联合访问路径的一部分。优化的是真实查询模式，不是孤立字段。

02

The default workhorse

B+Tree：为什么几层就能找到海量数据

PostgreSQL 和 InnoDB 的默认通用索引都建立在多路平衡树思想上。工程实现各有细节，但共同目标是：保持有序、降低树高、让等值与范围查询稳定。

Root

根页

搜索入口。缓存稳定时，它通常很容易留在内存中。

Internal

内部页

保存分隔键与子页指针；一次比较排除大量分支。

Leaf

叶子页

保存有序索引项。相邻叶页支持范围扫描和有序输出。

术语说明：PostgreSQL 官方名称是 B-tree

本章用“B+Tree 心智模型”帮助理解高扇出、叶层有序与范围扫描，但不把教科书结构和 PostgreSQL 的具体页格式画等号。实现细节以对应版本官方文档为准。

从根页比较搜索键

例如寻找 (tenant_id=42, created_at≈T)，先确定落在哪个键区间。

沿内部节点缩小范围

每层都有很高扇出，一页可指向许多下级页，因此千万级甚至亿级记录也只需很少层。

在叶子定位起点

等值查询读取匹配项；范围查询从起点沿叶页继续扫描，直到越过终点。

按地址访问可见行

PG 通常再访问堆页检查 MVCC 可见性；满足 index-only 条件时可跳过多数堆访问。

实验 2：树为什么一直不高？

LAB 02 / FAN-OUT

假设每个内部页平均可指向若干子页。调整记录规模与扇出，观察估算树高。真实树高还受键宽、填充率、版本与页分裂等影响。

估算层数—根到叶（含叶层）

扇出越高，树越矮；但“树高很低”只说明定位索引项便宜，不代表返回大量行和回表也便宜。

放到同一张 I/O 账单上：为什么通常选它？

B+Tree 不是每个单项都最快，而是把页友好、稳定树高、有序访问和持续更新放在一个结构里。数据库按页读写；内部页只承担导航时，同一页能容纳更多分隔键和子页指针，高扇出便把一次定位压缩到少量页访问。所有叶子保持同一深度，树高不会像未平衡二叉搜索树那样因插入顺序退化；叶层有序又让一次定位可以自然接上范围扫描和排序输出。

DEFAULT DECISION比较的是数据库页上的访问与维护，不是只比较抽象复杂度。
结构它的强项相对 B+Tree 的取舍更适合何时选择
B+Tree 心智模型通用默认 高扇出、始终平衡；叶层有序，兼顾等值、范围、联合键左前缀访问、排序和唯一性。 单项能力未必最强；需要额外空间，写入要维护顺序并处理页分裂。 标量键主要做比较、范围或 ORDER BY，尤其是常见 OLTP 读写混合负载。
平衡二叉搜索树 有序查找，内存中的节点旋转与比较直观。 每个节点只有两个分支；若按节点直接落盘，树更高，一次查询更容易产生多次随机页访问。 内存数据结构；不直接按数据库页组织的场景。
教科书 B-tree 同样是多路、平衡、面向块存储的有序树。 记录指针或数据记录可分布在内部与叶节点；B+Tree 将它们集中在叶层，内部节点保存分隔键与子页指针，范围扫描路径也更统一。 与 B+Tree 属于同一家族；真实数据库实现应按引擎术语和页格式理解。
Hash 只做等值匹配时，定位路径可能更直接。 哈希值不保序，不能直接支持范围、前缀有序扫描或 ORDER BY，适用面更窄。 查询语义长期稳定为纯等值，并经实际计划证明更合适。PG 可创建 Hash 索引；InnoDB 没有对应的通用持久 Hash 索引。
LSM-tree 家族 先在内存聚合写入，再顺序落盘并合并有序文件，适合高写入吞吐。 用后台 compaction 以及读、写、空间放大换写入能力；它更像存储引擎组织方案，并非 PG / InnoDB 中可直接替换 B-tree 的索引类型。 优先写入吞吐，且系统能承担多层查询、后台合并及其延迟波动的存储引擎。
GIN / GiST / BRIN 等 分别处理包含与全文、空间与近邻、列值和物理页高度相关的超大表粗筛。 GIN 倒排项多、写维护较重；GiST 是否需要 recheck 取决于操作符类；BRIN 极小但只保存块范围摘要。 查询不是普通标量比较时；具体选择见第 06 章“索引工具箱”。
所以选 B+Tree，选的是通用性与可预测性。它用少量树层定位起点，再高效衔接最常见的等值、范围和有序输出，又能在持续写入下保持平衡；范围很宽时仍会扫描许多叶页和数据页。查询语义明显偏离这些能力时，再换专用结构。

B+Tree 擅长

=、<、<=、>、>=、BETWEEN、前缀可利用的匹配、范围扫描，以及与索引顺序一致的 ORDER BY。

B+Tree 不擅长

包含式数组/JSON 查询、任意位置模糊匹配、二维空间关系、与物理顺序高度相关的超大时序表摘要——这些有其他索引结构。

页分裂：有序结构的写入账单

B-tree 必须始终保持键有序。新键应该落入的叶页还有空间时，只需插入；目标页已满时，就要申请新页、在两个页之间重新分配索引项，并把新的分隔键写入父页。父页也满时，分裂还可能向上级联。

更准确的结论：不要无条件排斥 UUID；应避免“随机、过宽、字符串存储的 UUID”成为高写入表的聚簇主键。若需要全局唯一，可评估 UUIDv7、ULID 类有序标识，或使用内部窄主键加外部 UUID 唯一键，并用真实并发与索引规模验证。

PostgreSQL 的 MVCC 让故事更复杂

更新通常产生新的 tuple 版本。若更新未涉及任何索引列、且同一堆页有空间，HOT 更新可以避免为新版本创建新的索引项；给“经常更新但不参与查询”的列乱加索引，可能顺手堵住这条优化路径。这里的堆页行为与 B-tree 索引页分裂是两笔不同的账。

InnoDB 的主键就是数据组织方式

聚簇索引的叶记录包含整行；二级索引叶记录保存二级键和主键值。因此主键既要考虑写入顺序，也要尽量短小稳定。过宽主键会被复制进每个二级索引，放大空间、缓存和 I/O 成本。

先认识五条常见路径

节点人话常见适用场景排查重点
Seq Scan顺序读表页并过滤返回比例大、表小、无可用索引扫描多少页、过滤掉多少行
Index Scan查索引，再逐条访问堆命中比例低的点查/小范围回表是否随机、候选是否过多

看计划的顺序

  1. 从最深层数据源看起，再向上读。
  2. 比较每层估算行数与实际行数。
  3. 把 actual rows × loops 放进脑中。
  4. 找大量丢弃、重复循环、读页和落盘排序。
  5. 确认最终只为多少返回行付账。

两条安全红线

EXPLAIN ANALYZE 会真实执行 SQL。对 INSERT/UPDATE/DELETE 使用时会产生写入、触发器、锁与 I/O；即便事务最后回滚，中间影响仍发生。

生产执行前评估查询时长和系统压力。先用普通 EXPLAIN、只读副本或受控参数，再决定是否实跑。

成本不是毫秒。PG 计划中的 cost 是优化器的相对单位；只有使用 ANALYZE 后的 actual time 才是本次实际时间，而且它也不是跨环境基准。

优化器靠什么猜？统计信息

PostgreSQL 会采样并记录空值比例、不同值数量、最常见值、直方图、物理相关性等信息。单列统计无法自动理解 tenant_id 与 status 的业务相关性；当多列相关性导致严重误估，可考虑扩展统计，而不是盲目提高所有列的统计目标。

-- 更新 orders 的统计信息
ANALYZE orders;

-- 多列依赖与常见值组合：只在确有误估证据时创建
CREATE STATISTICS st_orders_tenant_status
  (dependencies, mcv)
ON tenant_id, status FROM orders;
ANALYZE orders;

不要用 enable_seqscan = off 证明索引“更好”

它最多帮助做诊断对照，不能替代真实成本验证。强迫一条路径能跑，不代表它在生产分布、缓存和并发下更便宜。

04

One query, one shape

联合索引：顺序是访问路径，不是口诀

给 tenant_id、status、created_at 各建一个索引，和为订单列表设计一个联合索引，不是同一件事。

三个单列索引

PG 可能用 BitmapAnd 合并候选 TID，这对中等选择性很有价值。但位图组合通常不能直接交付 created_at DESC 的顺序，仍可能需要排序。

CREATE INDEX ON orders (tenant_id);
CREATE INDEX ON orders (status);
CREATE INDEX ON orders (created_at);

面向查询形状的联合索引

索引先按租户分段，再按状态分段，然后在段内按时间和 ID 有序。它能把过滤边界与分页顺序放在同一条路径上。

CREATE INDEX idx_orders_feed
ON orders
  (tenant_id, status, created_at DESC, id DESC);
不要从“有哪些字段”开始建索引。先固定一条高频 SQL 的 WHERE + ORDER BY + LIMIT，再把它翻译成一条有序访问路径。

从一条 SQL 推导联合索引：五步创建法

固定查询形状

把必填、可选条件、排序和分页写完整。不同条件组合可能是不同形状，不要先追求一条索引包办全部。

排列等值边界

把稳定的 = 条件作为左侧导航键；顺序优先服务重要的单列前缀、租户边界与复用需求。

接上范围与排序

等值列之后放时间等范围列，并让后续顺序匹配 ORDER BY。进入范围后，右侧列通常难再缩小连续扫描区间。

补稳定边界

排序值可能重复时追加唯一、稳定的 id；游标条件、排序方向和索引顺序保持一致。

控制宽度并验证

返回列按收益决定是否 INCLUDE；用代表性参数检查计划、读页、写放大和重复索引。

两个等值列，谁在前？

EQUALITY TIE-BREAKER
总是同时出现

对这条查询，(tenant_id, status) 与 (status, tenant_id) 通常都能定位同一组合，差异往往不大。

存在单列查询

哪个重要条件会单独出现，哪个更值得成为左前缀。例如常查某租户全部订单，就让 tenant_id 在前。

条件有时缺席

若 status 可选，把它夹在时间前会破坏“不按状态”时的连续时间顺序；通常应为高频形状准备另一条索引。

因此：不要机械套用“区分度最高的等值列在前”。当等值列总是一起出现时，应按前缀复用、业务边界和查询变体裁决；本例选择 tenant_id 在前，是因为租户是稳定边界，而不是因为它一定更“快”。

“最左匹配”应该怎么理解

对于多列 B-tree，领先列上的约束最能缩小需要扫描的索引范围。缺少领先列时，后续列不是“物理上消失”，数据库仍可能扫描索引并过滤，但通常不能直接跳到一个很小的连续区间；是否值得用，要看成本。

版本注：PostgreSQL 18 才加入多列 B-tree skip scan

本教程以 PG 14–17 的保守基线讲解：缺少领先列通常无法高效定位。PG 18 的 skip scan 能在合适的数据分布下为缺失领先列重复发起定位，但它不是“列顺序从此不重要”。

MySQL 8.x 也不是一句口诀能讲完

InnoDB 联合索引遵循左前缀访问规律；MySQL 8.0.13 起对部分场景提供 Skip Scan。是否出现仍取决于成本、列分布、谓词与版本，以实际 EXPLAIN 为准。

查询形状 A：状态必填

WHERE tenant_id = $1
  AND status = $2
  AND (created_at, id) < ($3, $4)
ORDER BY created_at DESC, id DESC
LIMIT 50;

(tenant_id, status, created_at DESC, id DESC) 很自然。

查询形状 B：状态不传

WHERE tenant_id = $1
  AND (created_at, id) < ($2, $3)
ORDER BY created_at DESC, id DESC
LIMIT 50;

中间缺少 status，跨状态的时间顺序不再天然连续；另一条 (tenant_id, created_at DESC, id DESC) 可能更合适。

为什么排序要加 id

created_at 可能重复。只按时间分页，会让边界不唯一，产生重复或遗漏风险。将唯一且稳定的 id 作为 tie-breaker，索引顺序、ORDER BY 和游标比较必须保持一致。

展开 30 秒例子：只记时间为什么会漏一条？
第一页 · LIMIT 2 ID 10710:00:00 ID 10610:00:00 · 边界
游标必须保存
(10:00:00, 106)
第二页 · 正确继续 ID 10510:00:00 ID 22009:59:59

若游标只记 10:00:00，使用 created_at < 10:00:00 会漏掉 ID 105；改用 <= 又可能重复前一页。完整边界应写成 (created_at, id) < ('10:00:00', 106)。

不存在“一个完美索引覆盖所有可选条件”。给高频查询形状有限分型，远胜于为参数组合制造指数级索引。
05

Where is the row?

回表与覆盖：PG 和 InnoDB 不是同一条路

“回表”是方便沟通的词，但 PostgreSQL 堆表和 InnoDB 聚簇表的物理路径不同。混在一起讲，会直接带偏索引设计。

PostgreSQL heap

索引项 → TID → 堆 tuple

  1. B-tree 找到键与堆地址 TID。
  2. 访问堆页，依据 MVCC 判断版本可见性。
  3. 从可见 tuple 读取索引中没有的列。

Index Only Scan 只有在所需值可由索引返回、并且可见性条件允许时，才能免去堆访问。

NOT THE SAME
MySQL / InnoDB

二级索引 → 主键 → 聚簇记录

  1. 二级 B-tree 找到二级键和主键值。
  2. 用主键再次查聚簇 B-tree。
  3. 聚簇索引叶记录中取得整行。

若二级索引已经包含查询所需列，就可能成为 covering index，避免第二次按主键查整行。

不要把 PostgreSQL 主键叫作 InnoDB 式聚簇索引

PostgreSQL 的主键默认是唯一 B-tree，叶项指向堆表 TID；它不会持续让堆表按主键顺序物理组织。CLUSTER 可以按某个索引一次性重排表，但后续写入不会自动维持该顺序。

PostgreSQL：INCLUDE 是载荷，不是导航键

CREATE INDEX idx_orders_feed_cover
ON orders (tenant_id, status, created_at DESC, id DESC)
INCLUDE (user_id, total_cents);

user_id 和 total_cents 可以从索引叶项返回，但不能用来缩小这个索引的搜索范围，也不属于它的键顺序。宽列会膨胀索引项，甚至触碰索引元组大小限制。

Requirement 01

值在索引里

查询所需列必须能由索引类型保存或重建；B-tree 总是支持，GIN 通常不支持 index-only scan。

Requirement 02

堆页 all-visible

PG 的可见性信息不在普通索引项里。若堆页不是 all-visible，仍需访问堆确认。

Requirement 03

收益大于宽度

读少量返回列、更新相对少的表更可能获益；宽而频繁更新的覆盖索引可能得不偿失。

展开原理：为什么 Index Only Scan 仍可能访问堆？

PostgreSQL 的 MVCC 允许同一行暂时存在多个 tuple 版本。索引可以提供查询列和堆地址 TID，却没有 tuple 头部的 xmin/xmax 等信息，因此不能单独判断某个版本对当前事务快照是否可见。

① B-tree 索引项查询列 + TID
例如 P42 / #9
→
② Visibility Map检查 TID 所在的堆页 P42 是否标记为 all-visible
→
是：整页所有 tuple 已被保守地确认可见，直接使用索引值，不访问堆。
否：不能据此判断，访问 P42/#9 的 tuple 头部，结合当前快照检查可见性。
INSERT / UPDATE / DELETE清除相关堆页的 all-visible 位→VACUUM检查、清理后确认整页安全→重新标记 all-visible

页级保守标记一条记录刚被修改，就可能让同页其他记录也暂时需要回堆确认。

不是缓存状态堆页即使已在 shared buffers 中，不是 all-visible 仍要访问；只是未必产生物理磁盘 I/O。

看 Heap FetchesHeap Fetches: 0 才表示本次没有为可见性回堆；高频写入表通常更难长期保持。

节点名叫 Index Only，不保证本次真的“零堆访问”。写入频繁、autovacuum 尚未推进可见性映射时，Heap Fetches 可能很高。

MySQL 没有与 PG INCLUDE 完全相同的语法

通常把返回列放在复合索引尾部来形成覆盖。因为 InnoDB 二级索引还会携带主键，SELECT 主键可能已经被覆盖。请在 EXPLAIN 的 Extra 中观察 Using index，同时核算索引宽度。

06

Choose the right instrument

PostgreSQL 索引工具箱：B-tree 不是万能钥匙

本节先看 PostgreSQL 的 GIN、GiST、SP-GiST、BRIN 与 Hash；随后再单独对照 MySQL。选结构前，先描述搜索语义：等值、范围、包含、相似、空间关系，还是物理顺序上的大范围过滤。

Ordered

B-tree

适合：等值、范围、前缀有序访问、排序、唯一约束。

代价：键宽、页分裂、写维护；不擅长包含式复杂值。

Postings

GIN

适合：数组、JSONB、全文、pg_trgm 多词元查询。

代价：写入与维护较重，操作符类决定能回答什么。

Geometry

GiST

适合：范围重叠、空间、近邻、可扩展搜索策略。

代价：通常可能有损并需 recheck；效果依操作符类。

Search tree

SP-GiST

适合：天然可分区的空间，如 trie、四叉树、基数树。

代价：场景专用，不是普通 B-tree 的替代品。

Tiny summary

BRIN

适合：超大追加表，时间与物理位置高度相关。

代价：页范围摘要是有损的，需要 recheck；相关性差会读很多候选块。

Exact only

Hash

适合：只做等值比较的场景。

代价：不支持范围和排序；多数业务先验证 B-tree 是否已经足够。

Quick selector

索引类型问诊台

TOOL / FIRST GUESS

给出数据形态和搜索语义，得到“第一个值得验证的候选”。这不是自动建索引建议，最终仍需结合操作符类和执行计划。

B-tree从默认有序索引开始验证；如果查询语义不是比较运算，再换工具。

三种值得掌握的“索引形态”

Partial

部分索引

只索引稳定且高价值的子集，例如未删除、待处理订单。索引更小，但查询条件必须能在规划时推出索引谓词。

Expression

表达式索引

索引标准化后的值，例如 lower(metadata ->> 'customer_email')。查询要使用等价表达式；写入时要计算并维护结果。

Covering

覆盖索引

把高频查询的返回列带进索引，减少表访问。它优化的是读取路径，也会扩大索引和写入成本。

-- 部分索引：只维护未删除的高频订单
CREATE INDEX idx_orders_open_feed
ON orders (tenant_id, created_at DESC, id DESC)
WHERE deleted_at IS NULL AND status IN ('NEW', 'PAID');

-- 表达式索引：大小写无关邮箱查找
CREATE INDEX idx_orders_email_lower
ON orders (lower(metadata ->> 'customer_email'));

-- JSONB：更紧凑的 jsonb_path_ops 支持范围较窄，先核对操作符
CREATE INDEX idx_orders_metadata_gin
ON orders USING gin (metadata jsonb_path_ops);

-- 模糊包含搜索：需要 pg_trgm 扩展
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_orders_email_trgm
ON orders USING gin ((metadata ->> 'customer_email') gin_trgm_ops);
展开：为什么部分索引与参数化查询容易错过彼此？

PG 必须在规划阶段证明查询的 WHERE 条件蕴含部分索引谓词。它不是通用定理证明器，通常要求表达式直接匹配或能做简单不等式推导。诸如 x < $1 的参数化条件无法对所有参数值证明蕴含 x < 100，因此该部分索引可能无法使用。

展开：GIN 的 jsonb_ops 与 jsonb_path_ops

默认 jsonb_ops 支持更广的 JSONB 操作符；jsonb_path_ops 通常更小、对支持的包含/jsonpath 查询更专注，但不支持所有默认操作。不要把“更小”误译成“所有 JSON 查询都更快”。

07

Scale changes the bill

亿级数据：树未必很高，账单一定更厚

B-tree 高扇出让树高增长缓慢，但索引体积、缓存工作集、写放大、维护窗口和扫描范围都会随数据增长。大数据优化首先是减少访问范围。

Reduce

先裁剪

用租户、时间窗、生命周期或分区裁剪，把“不该参与本次查询”的数据排除在访问路径之外。

Locate

再定位

在剩余范围内使用合适索引，处理等值、范围、排序、包含等具体语义。

Sustain

最后算维护

核算写入、WAL、复制、vacuum、备份与并发建索引；能跑一次不等于能长期稳定运行。

BRIN：用极小摘要换取“先排除大段”

BRIN 为连续的堆块范围保存摘要，而不是给每一行保存精确指针。如果 created_at 与物理写入顺序高度相关，它能快速排除大量不相交的块范围；命中的范围仍要回表 recheck。

CREATE INDEX idx_orders_created_brin
ON orders USING brin (created_at)
WITH (pages_per_range = 64);

适合

追加式事件、日志、订单流水；查询按时间扫较宽范围；物理相关性高；希望索引非常小、写维护低。

不适合

随机更新使时间与物理位置混乱；要求单行精确点查；过滤后仍命中大部分块范围。

分区：管理和裁剪，不是“大号索引”

按月分区能让时间条件触发 partition pruning，也方便归档或删除旧数据；但每个被访问的分区内部仍可能需要索引。过多小分区会增加规划、元数据与运维负担。

策略最适合解决主要风险验证信号
时间分区保留策略、时间裁剪、冷热分层跨期查询触碰多分区计划中实际扫描的分区数
租户分区极少数超大租户隔离租户数量高、分布变化热点和倾斜是否可控
BRIN相关性高的超大追加表相关性差导致大量 recheck索引大小、候选块、相关性
B-tree精确定位和小范围有序读取大工作集挤出缓存、写维护扫描条目、读页、索引大小

每多一棵索引，每次写入多一份维护

索引会增加插入与更新的 CPU、缓存、WAL、复制流量和磁盘占用。更新被索引列还可能减少 PostgreSQL 使用 HOT 更新的机会。

删除并不会立刻把所有空间还给操作系统；MVCC 清理、vacuum 和索引膨胀要分别理解。普通 VACUUM 主要让空间可复用，不等于缩小文件。

删除索引前先审计

idx_scan = 0 只是线索：统计可能刚重置，索引可能支撑唯一约束，或只在低频但关键的月末任务中使用。结合完整观察周期、约束、查询日志与依赖再决定。

-- 使用情况：结合统计重置时间和业务周期解读
SELECT schemaname, relname, indexrelname, idx_scan,
       pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
WHERE relname = 'orders'
ORDER BY pg_relation_size(indexrelid) DESC;

CREATE INDEX CONCURRENTLY 不是“无锁且免费”

它允许普通写入继续进行，但需要多阶段扫描与等待，会消耗明显 I/O 和 CPU，且不能放在事务块中。失败可能留下 invalid index，需要检查并处理；发布前要准备资源评估、监控和回滚。

大数据第一原则：先让绝大多数数据不参与，再让剩下的数据找得快；不要指望单个巨型索引替你解决生命周期和访问边界。

The frontend is in the query plan

数据库只看到最终查询，但查询形状常由产品和接口契约决定。任意排序、深页码、无限时间窗与精确总数，都会变成数据库必须完成的工作。

万能 SQL：方便写，难以拥有稳定访问路径

One shape for everything 
WHERE tenant_id = $1
  AND ($2::text IS NULL OR status = $2)
  AND created_at >= $3
ORDER BY created_at DESC, id DESC;

当状态有时命中 5%、有时不传，真正的最佳访问路径可能不同。prepared statement 的 generic/custom plan 选择还会进一步影响参数敏感查询。

A few explicit templates 
-- 模板 A：状态必填
WHERE tenant_id = $1 AND status = $2
  AND (created_at, id) < ($3, $4)

-- 模板 B：不按状态过滤
WHERE tenant_id = $1
  AND (created_at, id) < ($2, $3)

由后端选择固定参数化模板，不是拼接用户输入。模板数量保持有限，并分别用代表性参数验证索引。

Repeatable investigation

慢接口排查手册：从症状到上线

把优化变成一条可复用、可审计的证据链。每一步都应该产生一个结论，而不是只产生一条新索引。

十步排查路径

定义“慢”

记录 p50/p95/p99、吞吐、超时率、业务影响和开始时间；平均值经常藏住尾延迟。

锁定真实查询形状

保存规范化 SQL、绑定值、返回行数、租户/状态/时间分布、并发量，而不只是 ORM 日志里带问号的模板。

分层定位

区分排队、连接池、锁等待、数据库执行、网络传输和应用序列化；别把端到端时间全算给索引。

取得代表性计划

先普通 EXPLAIN，再在安全环境用 EXPLAIN (ANALYZE, BUFFERS)；记录冷热缓存差异。

找最大工作量

比较估算/实际、loops、过滤丢弃、读页、Sort spill、Heap Fetches 和锁等待，不只盯着“最慢节点”标签。

验证统计与分布

数据刚批量变化就 ANALYZE；检查倾斜、多列相关性、父分区统计与参数敏感性。

提出最小改动

候选可能是改查询形状、游标分页、收窄返回列、一个联合/部分索引，或先限制时间范围。

做前后对照

在代表性数据上比较计划、读页、返回行、写入和索引大小；不要只跑一次耗时。

设计发布

评估建索引锁与资源、并发创建限制、复制延迟、迁移工具事务行为、回滚与监控阈值。

上线后复盘

持续观察计划稳定性、p95/p99、buffer/I/O、写入代价和索引使用；确认问题真的消失而非转移。

看到现象后，下一步问什么

证据优先假设下一步验证

Index Scan 但 read 很高候选多且回表分散、缓存偏冷命中比例、heap 相关性、覆盖价值、Bitmap 路径
Index Only 但 Heap Fetches 高可见性映射不足、表更新频繁vacuum 状态、all-visible 比例、索引是否过度覆盖

不要先加 Hint

Hint 可能暂时掩盖误估，却把数据增长后的选择空间锁死。先理解为什么选择当前计划。

不要只看一次

首次运行与再次运行的缓存状态不同；参数和租户分布也不同。记录一组代表性样本。

不要承诺倍数

“快 100 倍”只属于那次实验。对外承诺 SLO 和容量边界，而不是某台机器的一次比值。

优化完成的定义：真实请求的尾延迟与资源消耗达到目标，同时写入、空间、发布风险和长期维护成本仍可接受。

推荐实验路线

建立基线

先看无合适索引的订单列表计划，记下访问路径、实际行、过滤丢弃、buffers 与排序。

只加 tenant 单列索引

换成联合 B-tree

让等值条件、时间范围和稳定排序对齐，观察能否快速停止在前 50 行。

加入覆盖列

部分与表达式索引

比较待处理小集合和 lower(metadata ->> 'customer_email') 在建索引前后的计划。

GIN 与 BRIN

用 JSONB 包含和窄时间窗，分别观察倒排候选与页范围摘要的访问路径。

重复一次

比较首次和再次运行的 buffer 变化；不要把缓存收益误认为索引结构收益。

写下自己的结论

记录计划形状、读取页、索引尺寸和环境，而不是只记“快了多少倍”。

脚本会改什么？

为什么不用固定耗时？

Case closed

一页式速查：下次慢接口就照着问

把这一节单独打印出来，贴在工位边。索引优化的价值，不在于记住多少术语，而在于少走几次“先建再说”的弯路。

先问什么

  • 慢到多少：p50 / p95 / p99？
  • 哪组参数、哪个租户、什么时间窗？
  • 返回几行，端到端哪个阶段慢？
  • 偶发还是稳定，何时开始变化？

计划看什么

  • 估算行与实际行是否偏离？
  • actual rows × loops 有多大？
  • Buffers、过滤丢弃、Sort spill？
  • Index Only 的 Heap Fetches？

索引怎么想

  • 先确定高频查询形状。
  • 等值边界 → 范围/排序 → 返回列。
  • 联合顺序是否服务查询变体？
  • 部分、表达式或专用类型是否更小？

危险信号

  • 深 OFFSET、万能 OR。
  • SELECT *、无限日期、任意排序。
  • 估算偏差超过一个数量级。
  • 给每个字段各建一棵索引。

上线前后

  • 代表性数据与冷热缓存对照。
  • 写入、WAL、空间、复制代价。
  • 并发建索引、锁、失败与回滚。
  • 上线后观察计划稳定性和尾延迟。

常用 PG 命令

EXPLAIN (ANALYZE, BUFFERS) ...;
ANALYZE orders;
SELECT * FROM pg_stat_user_indexes
WHERE relname = 'orders';
最终心智模型：索引不是“让查询变快”的开关，而是把某类读取工作提前组织、持续维护的一份数据结构。
